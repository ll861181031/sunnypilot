# 摄像头调试 web 工具

一个**独立**的本地网页工具：选 1~2 个 V4L2 摄像头，设置分辨率/帧率，实时看每个相机的
**实测读取速率**，以及两路同时跑时的合计数率；并能把「同一设备单独跑」和「与另一台同时跑」
自动配对对比。

它不启动、不停止、不向任何别的进程发信号。相机被占用时它只报出占用者的 PID，
不会去关掉对方（行车栈里的 `camerad` 就是这样被保护住的）。

## 为什么需要它

这台机器上两台相机（2026-11-04 镜头调换后：DECXIN 主摄 + Realtek 广角）**共用一条 USB 2.0 总线**，任何一路的速率都受另一路
影响；而行车栈从来不报告「驱动实际给了多少 fps」。本工具就是补这个洞：数字全部来自
采集线程上真实的 `read()`，不是按请求值推算的。

## 快速开始

```bash
cd /data/sunnypilot
.venv/bin/python tools/camera_debug/camera_debug.py            # 默认 0.0.0.0:8099
```

浏览器打开 `http://<本机IP>:8099/`（本机就是 `http://127.0.0.1:8099/`）。

无硬件自测（提供 2 台虚拟相机，不碰真实设备）：

```bash
.venv/bin/python tools/camera_debug/camera_debug.py --fake 2
```

参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--host` | `0.0.0.0` | 监听地址；同网段可直接访问 |
| `--port` | `8099` | 监听端口 |
| `--fake N` | `0` | 额外提供 N 台虚拟相机（`fake:0`…），用于无硬件验证界面与 API |

## 界面

1. **选择相机与模式**：设备下拉只列出真正能出帧的节点（UVC 的 metadata 节点会被过滤，
   判据是 `v4l2-ctl --info` 的 `Device Caps`，不是设备级的 `Capabilities`——后者对
   `/dev/video1` 也写着 Video Capture）。分辨率/帧率下拉来自该设备**实际上报**的模式表。
   第二个相机默认关闭，勾上「使用」即可同时跑两路。
2. **实时速率**：每路一个卡片，大数字是**实测读取速率**（1 秒滑动窗口），下面是
   `read()` 阻塞时间分位、帧间隔分位与抖动、单帧大小/码率、采集线程 CPU、失败帧数；
   还画一条相对请求帧率的曲线。底部一行是**同时**的合计速率与合计码率。
3. **单独 ↔ 同时 对比**：每次「开始 → 停止」都会归档成一条会话；工具按
   「设备 + 模式」把同一设备**单独跑**的结果和**与另一台同时跑**的结果配对，算出差值。
   「导出 JSON / 复制摘要」用于留证据。

## 数字口径

- **配置 vs 协商**：配置是你要的值，协商是驱动真正接受的值（`cap.get()`）。UVC 会静默回退，
  两者不一致就说明请求没被满足（实测：请求 1344x760 被回退到 1280x720）。
- **实测读取速率**：采集线程每秒成功 `read()` 的帧数。这是唯一可信的速率口径。
- **预览不污染测量**：MJPG 模式下驱动给出的帧本身就是 JPEG，预览原样转发，
  **不解码也不重编**；需要编码时（YUYV 路径）发生在 HTTP 线程而不是采集线程。
- **采集线程 CPU** 用 `time.thread_time()`，只统计该采集线程，不含预览/HTTP。
- **勾选「测 PyAV 解码耗时」**才会额外做一次 MJPEG→NV12 解码耗时测量，和行车栈的解码路径一致。

## 本机实测（2026-10-16，行车栈未运行）

三轮完整测量（每轮 8 秒；`平均`含启动爬升，看速率请以 1 秒滑动窗口为准）：

| 场景 | 请求 | 协商 | 实测(窗口) | 平均 | 码率 | dt p99 | read() 阻塞 p50 | CPU |
|---|---|---|---|---|---|---|---|---|
| 长焦 `/dev/video2` 单独 | 1920x1080@30 MJPG buf1 | 1920x1080@30 | **20.0 fps** | 19.0 | 2.58 MB/s | 52.2 ms | 51.8 ms | 0.2% |
| 广角 `/dev/video0` 单独 | 1280x720@20 MJPG buf2 | 1280x720@20 | **20.0 fps** | 17.9 | 0.97 MB/s | 52.2 ms | 50.0 ms | 0.2% |
| 两路同时 | 同上 | 同上 | 长焦 20.0 / 广角 20.0 | 19.1 / 17.9 | 3.52 MB/s | 52.1 ms | 51.9 ms | 各 0.2% |

工具给出的对比结论：

```
/dev/video2  1920x1080 MJPG: 单独 18.99fps(2.579MB/s) -> 同时 18.96fps(2.446MB/s)  变化 -0.2%
/dev/video0  1280x720  MJPG: 单独 17.88fps(0.969MB/s) -> 同时 17.88fps(0.940MB/s)  变化 -0.6%
```

即**在这两个设置下，两路同时跑几乎没有互相拖慢**（合计 40 fps / 3.52 MB/s ≈ 28 Mbit/s，
离 USB 2.0 的实际上限还很远）。也就是说，广角这套参数本身是安全的。

两个真正测得出来的结论（都是工具直接给出的，不是推算）：

1. **请求 30 fps 不兑现**：长焦在 1920x1080 MJPG 下驱动接受 `--set-parm=30` 并回读 30 fps，
   但实际只给 20 fps（帧间隔 p99 ≈ 52.1 ms）。用 `v4l2-ctl` 绕开 OpenCV 独立交叉验证过：
   100 帧耗时 5.46 s（18.31 fps）、自报 19.98 fps —— 与工具读数一致，不是工具的偏差。
2. **缓冲深度是硬开关**：广角 1280x720@20 下，
   `buffersize=1` → **10.0 fps（dt 100 ms）**，`buffersize=2` → **20.0 fps（dt 52 ms）**。
   这就是 `camera.py` 给广角单独留 `WIDEBUFFERSIZE=2` 的原因，工具里可以直接来回切着看。

另外：请求长焦不支持的 1344x760 时，界面同时显示「请求 1344x760」与「协商 1280x720」
并给出告警 —— 驱动会静默回退，不测就发现不了。

占用路径也已验证：另一个进程持有时开始采集会得到
`无法打开 /dev/video2（被 PID 421788 占用）`，而不是静默失败或去杀那个进程。

## 让两路帧率完全一致：`buffersize` 必须 ≥2（2026-10-16 实测）

**现象**：两台相机设成同样的分辨率/帧率，长焦 30 fps 而广角只有 15 fps。

**根因**：`buffersize=1`。V4L2 单缓冲时驱动无法在应用持有当前帧时排队下一帧，
相机于是**丢掉约一半的帧**——广角的 `dt50` 正好是 2×33.3 ms（15 fps）。
`dt50` 是判断依据：它等于 2 倍请求间隔就说明在丢帧，而不是相机能力不足。

**修复**：把缓冲设成 **2**（工具现在两路都默认 2，默认模式也改成实测一致的
**1920x1080@30**）。实测（1920x1080@30 MJPG，40 秒连续采样）：

| buffersize | 长焦 `/dev/video2` | 广角 `/dev/video0` | 一致 |
|---|---|---|---|
| **1** | 30.0 fps | **15.0 fps**（dt50 67.97 ms） | 否 |
| **2** | 30.0 fps（dt50 32.02） | **30.0 fps**（dt50 32.01） | **是** |
| 3 | 25.0 fps | 30.0 fps | 否 |

buf2 那次 40 秒里两台**帧数 1191 vs 1191（差 1 帧）**、平均帧率都是 29.4 —— 真正对齐了。

**同一台机器上其它组合的实测**（1920x1080、buf2）：

| 请求 | 长焦 | 广角 | 一致 |
|---|---|---|---|
| @30 | 30.0 | 30.0 | **是** |
| @25 | 25.0 | 25.0 | **是** |
| @20 | 18.0 | 20.0 | 否 |
| @15 | 15.0 | 14.0 | 否 |
| 720p@20 | 18.0 | 20.0 | 否 |

**要一致就用 30 或 25**；请求 20/15 时两台会各自就近取档，反而不齐。

**两个坑**：

1. **别用几秒钟的短测下结论**。前 4 秒还在爬升（实测 t+4s 时长焦窗口只有 21.0 fps），
   平均帧率要到 ~20 秒才稳定。至少跑 20 秒再比。
2. **暗光会让相机自己降帧**。长焦有 `exposure_dynamic_framerate=1`（广角没有这个开关），
   曝光顶到上限时它会从 30 掉到 20。要它守住请求值可以关掉：
   `v4l2-ctl -d /dev/video2 -c exposure_dynamic_framerate=0`（代价是画面变暗）。
   所以"两路一致"要在同一光照下确认。

## 两路同时采集：能跑，但受 USB 总线预留影响（2026-10-16 更新）

**先说结论：两路 1920x1080 可以同时采集。** 当天 23:1x 实测（长焦 + 广角，均在 `usb1`）：

| 相机 | 请求 / 协商 | 实测 | 码率 | 失败 |
|---|---|---|---|---|
| `/dev/video2` 长焦 | 1920x1080@30 MJPG | **20.0 fps** | 2.92 MB/s | 0 |
| `/dev/video0` 广角 | 1920x1080@30 MJPG | **15.0 fps** | 4.01 MB/s | 0 |
| 合计 | | **35 fps** | 6.92 MB/s | 0 |

那一次开机**没有任何 `Not enough bandwidth`，也没有掉线**。

**不是网页/浏览器的限制**：用无头 Chrome 同时接入两路 MJPEG 预览，两路都在实时刷新
（各 8 个不同采样帧、naturalWidth 均为 1280x720）。浏览器对同一 host 可开 6 条连接，
两路预览只占 2 条。

**但失败确实发生过一次**（当天 19:06 / 19:08，同样的两台相机）：

```
usb 1-2: Not enough bandwidth for new device state.
usb 1-2: Not enough bandwidth for altsetting 11
```

机制是：**USB 核心按 UVC 要切换到的 altsetting 预留带宽，不按实测平均码率。**
DECXIN 描述符里的预留量：

| altsetting | wMaxPacketSize | 预留带宽 |
|---|---|---|
| 1 | 1×192 | 12 Mbit/s |
| 6 | 1×944 | 60 Mbit/s |
| 10 | 3×960 | 184 Mbit/s |
| **11** | **3×1020** | **196 Mbit/s（24.5 MB/s）** |

USB 2.0 高速的等时预算约 42 MB/s，altsetting 11 一次要走掉 24.5 MB/s；两台相加就可能超。
所以「一路才几 MB/s」与能否同时跑**不是同一个量**——决定成败的是预留量。

**为什么 19:06 失败、23:1x 成功，目前只有相关性证据，没有定论**：两次的差别是
① 相机插在不同 USB 口（19:06 时广角在 Hub 后面 `1-1.2`，现在两台都在根口 `1-2`/`1-4`）；
② 请求的模式可能不同（当时页面还会默认选到 4K，现在默认 1280x720）。
**相机的 USB 描述符与固件标识当天没有变化**（`bcdDevice 6.79` / `0.04`、序列号、
altsetting 表与 4K 帧描述符逐字节一致），所以这不是"相机固件变了"能解释的。
要定论需要按变量逐个复测（同一组 USB 口下改模式、同一模式下改插口）。

工具现在的做法是**陈述事实、指向日志**，而不是替你下结论：

- 设备下拉与实时卡片显示每台相机的总线位置（如 `usb1:1-2`、`usb1:1-1.2（经 Hub）`）；
- 选了两台**同总线**相机时，页面与 API 都提示"共用一条总线的等时带宽；本机实测
  1080p+1080p 可以同时跑"，并说明真起不来时看 `journalctl -k | grep -i bandwidth`；
- 采集线程失败时的提示同样指向该日志。

另：长焦在 19:13:38 **从 USB 总线上掉线**（`/dev/video2` 节点消失）、21:07 重启后
DECXIN 枚举 15 秒又断开、23:03～23:08 又插拔数次。**掉线时节点不存在，任何工具都采不了**，
需要重新插拔——这与带宽无关，是物理层/供电/接触问题。

**能同时跑的两条路**：① 把两台相机降到都能容纳的设置、或把其中一台换到**另一条 USB 总线**
（这台机上 `usb3/usb5/usb7` 是独立的 480M 根集线器，`usb4/usb6/usb8` 是独立的 10000M）；
② 只开一台。物理口对应哪条总线用 `lsusb -t` 一看便知。

## 与行车栈的关系

- 采集期间相机被本工具**独占**。排查完先停采集，再启动行车栈。
- 反过来若 `camerad` 正在跑，本工具会打不开并显示占用 PID —— 不会互相破坏。
- `Ctrl-C` / `SIGTERM` / 正常退出都会释放相机（已实测：SIGTERM 后进程退出、端口释放、
  `/dev/video*` 无任何 fd 占用）。

## 安全

默认监听 `0.0.0.0` 且**没有鉴权**：同网段任何人都能打开页面、占用相机、查看画面。
只在家里的内网使用；需要收紧就用 `--host 127.0.0.1`。
